# Autonomous Compression Swarm (ACS)

Datran is a self-hosted file-sharing platform built on a **self-optimizing, evolutionary compression network**.

- Compression nodes ("reactors") evolve the best way to compress each kind of content, using the files people actually upload.
- They store files in a deduplicated, self-reorganizing object store.
- They move data toward the nodes where it is requested.
- They predict which files will be needed next and prepare them in advance.

Every byte is stored losslessly and verified on write and on read.

Every figure in this document was measured. Section 9 explains how to reproduce the numbers on your own data.

---

## 🚀 Features

| Feature | What it does |
| :--- | :--- |
| **Emergent Speed** | Per-content-type compression recipes evolve on real uploads, scored by size saved minus encode/decode time. The best ones are shared across the network. |
| **Data Gravity** | Files replicate to the nodes where they are requested, and cold copies are dropped when they're safely replicated elsewhere. |
| **Self-Rewriting** | Storage is split into deduplicated chunks. Chunks that occur or are read together are fused into super-chunks, and split again if that stops paying off. |
| **Polyglot API** | One HTTP API described by an OpenAPI 3.1 spec, with tested clients for Python, Rust, C++ and TypeScript. |
| **Generative Compression** | Data produced by a simple rule is stored as that rule: lossless and exact. |
| **Temporal Precognition** | Downloads are predicted from time-of-week patterns, recency and "what gets opened next", and the files are prepared before they're requested. |

**What these features cannot do.** These are limits of mathematics and physics, not of the implementation:
- **Generative compression only shrinks data that really is generated by a simple rule.** Examples are fills, repeating blocks and counters. On such data it measured **61,511×** (64 MiB down to 1,091 bytes). Random or already-compressed data cannot be compressed losslessly by anyone, so it is stored as-is, costing only a few bytes.
- **Prediction cannot make latency zero.** A predicted download is served from memory and skips storage reads and decompression, but the network transfer still takes time.

## 📦 Installation & Usage

### Prerequisites
- Node.js 24 (its built-in zstd is used by the fallback decoder)
- Rust stable toolchain, with a C compiler for zstd
- Optional: PostgreSQL (otherwise a local JSON database is used)

### Setup
```bash
npm install && (cd diocom-app && npm install)
cp diocom-app/.env.example diocom-app/.env.local   # set DIOCOM_SECRET at minimum
npm start                                           # reactor on :3005 + web app on :3001
```
`npm start` launches the reactor (running `cargo run --release` if no binary is built yet), generates a shared reactor token, and starts the web app with `STORAGE_BACKEND=reactor`.

### Production (HTTP/3)
`deploy/` contains:
- a Caddy reverse proxy: HTTP/3 over QUIC on UDP 443, HTTP/2 fallback, automatic TLS, settings tuned for streaming large transfers, security headers, and compression for text types only
- a `docker-compose.yml` that runs the proxy, the app and the reactor (the reactor port is never exposed publicly)

See [deploy/README.md](deploy/README.md) for setup, firewall rules (open UDP 443) and how to verify that `h3` is in use.

### Running a cluster
Start every reactor with the following settings:

```bash
REACTOR_BIND=0.0.0.0
REACTOR_PEERS=http://node-b:3005,http://node-c:3005
REACTOR_TOKEN=<shared>   REACTOR_CLUSTER_TOKEN=<shared>
REACTOR_MIN_REPLICAS=2   REACTOR_REGION=eu-north     # optional
REACTOR_TLS_CERT=... REACTOR_TLS_KEY=... REACTOR_TLS_CA=...   # recommended across hosts
```
A reactor refuses to listen on a non-loopback address unless both tokens are set.

## 🔌 API Reference

The full contract is [core-reactor/openapi.yaml](core-reactor/openapi.yaml). Client libraries live in [clients/](clients/).

| Method | Path | Purpose |
| :--- | :--- | :--- |
| POST | `/compress`, `/decompress` | Compress a blob with the evolved recipe for its content type, or decode one |
| PUT | `/store/files` | Store a file (streamed). Returns `file_id` (SHA-256), `stored_bytes`, `new_bytes`, the dedup counts and the content class. |
| GET/HEAD | `/store/files/:id` | Read a file. Supports `Range`, served from anywhere in the cluster. |
| DELETE | `/store/files/:id` | Unpin a file. When nothing pins it, a tombstone is created and propagates cluster-wide. |
| GET | `/store/stats` | Dedup, compression, packs, fusion, scrub and garbage-collection status |
| GET | `/evolution/status` | Evolution state per content type: generation, champion recipe, fitness, measured speeds |
| GET | `/cluster/status` | Peers, holder samples, demand, pulls/drops/repairs, remote reads |

- **Auth:** `/health` is open. Every other endpoint needs the `x-reactor-token` header.
- **Node-to-node endpoints** (`/cluster/inventory`, `/manifests`, `/objects`, `/chunks`, `/hold`, `/unpin`) use `x-cluster-token`. They are documented as internal.

| Client | Install / location | Notes |
| :--- | :--- | :--- |
| Python | `clients/python` | Standard library only, Python 3.9+, typed |
| Rust | `clients/rust` | async, reqwest + rustls |
| C++ | `clients/cpp` | C++17, header-only, no dependencies. Plain HTTP; use a TLS proxy across hosts. |
| TypeScript | `clients/typescript` | fetch-based, no runtime dependencies |

## 🧠 Architecture

### 1. The Genome: evolutionary compression (`core-reactor/src/evolution.rs`)
- **Content classes:** each upload is sorted by MIME type plus byte sniffing into `text/json`, `text/plain`, `text/csv`, `text/markup`, `binary/numeric`, `binary/structured` or `media/compressed`. `media/compressed` is stored as-is.
- **Genome:** a recipe made of:
  - a codec: zstd, brotli, LZ4, deflate, procedural or raw
  - the codec's level and window size
  - a pre-filter: delta or byte-shuffle, with a stride of 1, 2, 4 or 8
  - an optional trained zstd dictionary
- **Population:** 12 recipes per class. Each generation, the top 4 survive and the rest are refilled by crossover, mutation and recipes from peers.
- **Fitness:** `ln(ratio) − 0.5·encode s/MiB − 1.0·decode s/MiB`, measured on held-out samples of real uploads.
  - Dictionaries are trained on one half of the samples and every recipe is scored on the other half, so results reflect data the system hasn't seen.
  - A recipe that fails the lossless check scores −∞.
- **Privacy:**
  - Samples stay in memory only.
  - Encrypted and password-protected uploads are never sampled.
  - Dictionaries contain fragments of user data, so sharing them with peers is opt-in (`REACTOR_SHARE_DICTIONARIES`).
- **Output format:** every blob records how it was encoded (codec, filter, original length, CRC-32, dictionary ID). Any past recipe can always be decoded, and the TypeScript fallback decodes every format.

### 2. Generative compression (`core-reactor/src/procedural.rs`)
- **The codec:** procedural, codec 5. Its program is made of FILL, REPEAT (periodic copy) and ARITH (counters of 1, 2, 4 or 8 bytes in either byte order) operations. Everything else is stored as literal bytes, compressed with zstd.
- **Speed:** detection runs at about 1.4–2 GiB/s on procedural data and about 120 MiB/s on random data.
- **Safety:** decoding is bounded by the original length recorded in the header, so a malicious program cannot become a decompression bomb.
- **When it's used:** it joins the evolution pool, and evolution picks it where it wins. On procedural records it scored 694× against 78× for the best general-purpose codec.

### 3. Self-rewriting storage (`core-reactor/src/store/`)
- **Chunking:** FastCDC content-defined chunks (16/64/256 KiB), addressed by SHA-256. Identical chunks across all files are stored once.
- **Storage:** chunks are compressed with the champion recipe. Small objects go into append-only pack files with a group commit (one fsync and one index commit per batch). Large objects are stored as individual files. The index is redb, which is ACID.
- **Fusion:** chunk runs that appear in several files, or are read together, are fused into a super-chunk, but only if that is measurably smaller or saves reads. Super-chunks that are mostly read piecemeal are split again. Each rewrite is crash-safe: write, verify and fsync, then one index transaction, and garbage-collect after a grace period.
- **Integrity:** every write is verified. Every read checks each chunk's hash, and a background scrub re-checks stored objects. Corrupt objects are quarantined and repaired from a peer.

### 4. Data gravity (`core-reactor/src/cluster/`)
- **Inventory:** nodes exchange versioned inventory deltas, tombstones, demand scores and capacity.
- **Remote reads:** a read of a file not held locally fetches only the objects it needs from a holder, verifies them and caches them.
- **Moving toward demand:** demand decays exponentially with a half-life of 1 hour by default. When local demand for a file passes `REACTOR_GRAVITY_PULL`, the node pulls a full replica, and dedup applies.
- **Dropping copies safely:** a cold replica is dropped only after enough other holders grant 10-minute hold-leases to keep `REACTOR_MIN_REPLICAS` copies. The node a file was first uploaded to (its origin) keeps it until another holder takes over that role through the same lease mechanism.
- **Repair:** under-replicated files are repaired by exactly one node, chosen deterministically.
- **Deletes:** tombstones remove a file everywhere, and a stale replica that rejoins cannot bring it back.
- **Transport:** optional TLS between nodes. All cluster traffic is authenticated and size-capped.

### 5. The Oracle: access prediction (`diocom-app/src/lib/predict/`)
- **Signals:** a decayed recency/frequency score, a 168-bin hour-of-week histogram per file, and a per-user first-order Markov model of "file opened next" (within 30 minutes).
- **Prefetching:** every minute, the most likely files for the next window are prepared in memory within `PREFETCH_MAX_BYTES`. On each download, the likely next files are prepared too. Preparing a file is also a read on the reactor, so data gravity sees the demand.
- **Privacy:** visitors are identified by user ID or by a salted HMAC of IP and user agent. Raw IP addresses are never stored, and events are kept for 30 days.
- **Metrics:** precision, recall, cache hit rate for predicted vs. unpredicted requests, and p50/p95 time to first byte for hits vs. misses. All are shown on the admin page.

### 6. Multi-core compression (`core-reactor/src/workers.rs`, `store/ingest.rs`)
- **Store uploads:** each upload is a three-stage pipeline:
  1. The request thread chunks, hashes and deduplicates, in order.
  2. A shared worker pool compresses the new chunks on all cores.
  3. A stager writes the results strictly in chunk order.
- **What stays the same:** the output is byte-identical to the single-threaded path. Memory per upload is capped by `REACTOR_INGEST_INFLIGHT_BYTES` (default 64 MiB).
- **Large blobs on `/compress`:** zstd blobs over `REACTOR_MT_THRESHOLD` (8 MiB) use zstd's built-in multithreading and still produce one standard frame.
- **Evolution timing:** evolution still times single-threaded encodes, so scores stay comparable.

### 7. Web app (`diocom-app`)
- **Uploads:** streamed with constant memory. A 1 GiB upload peaked at 226 MiB of server RSS, against 3.8 GB before. Each file is hashed as it arrives and verified against the reactor's file ID.
- **Downloads:** streamed with Range support.
- **Sharing:**
  - Password-protected links, with PBKDF2-SHA256 at 600k iterations and HMAC-signed unlock cookies.
  - Expiring links, with automatic cleanup.
  - Optional end-to-end encryption, in the chunked **DCE2** format (`src/lib/crypto/dce2.ts`):
    - **Key:** the per-file key is derived with HKDF from the key in the URL fragment, which never reaches the server.
    - **Chunks:** the file is encrypted in 1 MiB AES-256-GCM chunks. Each chunk's nonce binds its position and a final-chunk flag, so reordering, truncation and extension are all detected.
    - **Streaming:** the browser encrypts the file slice by slice. A Service Worker decrypts on the fly with Range support, so multi-GB files download and videos seek without being held in memory: a 300 MB file used about 107 MB in the tab.
    - **Compatibility:** files encrypted in the old single-shot format still open.
- **Peer-to-peer:** WebRTC data channels, with signaling via `/api/swarm/announce` or manual offer/answer. The UI shows only the transport the browser actually negotiated (h3, h2 or http/1.1, plus the data channel state).
- **Accounts:**
  - Email/password, Google, Facebook and passkeys.
  - Passkey logins use single-use server tokens.
  - Login, unlock and passkey endpoints are rate-limited.
- **Admin page:** live panels for evolution, the object store and cluster, and access prediction.

## 🏆 Benchmarks (measured, reproducible)

**Evolution on held-out files.** Corpus: 235 source, documentation and JSON files; 10 generations. Command: `cargo run --release --bin bench -- <dir>`.

| Class | Held-out files | zstd-3 | Evolved champion | Ratio | Fitness |
| :--- | ---: | ---: | :--- | ---: | ---: |
| text/plain | 113 | 3.04× | zstd-10 + trained dictionary | **3.58×** | 0.80 → 1.00 |
| text/json | 3 | 3.26× | zstd-8 | 3.42× | 0.74 → 0.77 |
| text/csv | 1 | 3.03× | brotli-5 | 3.35× | 1.10 → 1.18 |

Only `text/plain` has enough held-out files to be a solid measurement.

**Generative compression.** 64 MiB made of a u32 counter, a fill and a repeated block compressed to **1,091 bytes (61,511×)**, with an exact round trip. 64 MiB of random data cost 2 KB over raw (0.003%).

**Object store.** Command: `cargo run --release --bin store-bench`.

| Workload | Result |
| :--- | :--- |
| 725 MiB of build artifacts | dedup 1.50× × compression 2.89× = **4.32×** total. Reads 250–320 MiB/s with every byte verified. Fusion made the fused data 6.3% smaller and saved 4,002 object reads. |
| 236 small source files, 8 writers | 20 MiB/s and 2,323 files/s, with pack files and group commit |
| Small-file ingest, 32 writers | 6.2 → 16.7 MiB/s after adding pack files (same durability) |
| One 1 GiB upload, 1 → 4 → all 14 threads | 53–57 → 137–147 → 149–173 MiB/s. Beyond 4 threads, disk writes are the limit on this machine. |
| zstd encode alone, 1 thread → multithreaded | zstd-3: 350 → 1,255 MiB/s · zstd-9: 45 → 141 MiB/s |

**Prediction.** Simulated trace: a user who opens a report and then slides every weekday morning, plus background traffic, over 4 weeks. Overall cache hit rate was 41.6% with prefetch against 0.3% without. For the user's routine files it was 100% against 0%.
